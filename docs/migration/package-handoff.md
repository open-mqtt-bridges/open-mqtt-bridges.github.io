# Hand off an existing bridge package

Use one record per package in [the baseline](../../migration/packages.json). The organization owns the namespace; the source repository and Actions access change. All nine recorded packages were private, inherited source permissions, and granted only the old bridge repository the Actions **Admin** role. Recheck the live settings rather than assuming the baseline is still current.

| Step                         | Owner                                          | Evidence required to proceed                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Record the starting point | Package administrator                          | Existing package ID, name, linked source, visibility, inherited access, repository grants, existing reader access, current tags/platforms, and a successful authorized pull by digest. Keep identifiable grant details in a private record.                                                                                                                                                                                                                                                     |
| 2. Freeze publication        | Old bridge maintainer                          | Pause all old tag-, branch-, release-, and manually triggered publishers for this package. Let in-flight jobs finish. Keep the old source and its release assets accessible.                                                                                                                                                                                                                                                                                                                    |
| 3. Prepare the new publisher | Monorepo maintainer and package administrator  | Restrict the `bridge-release` environment to the `main` branch. Authorize only the intended bridge. Grant the monorepo the minimum package write access needed for the test; retain private visibility. Review inherited access **before** linking to the public monorepo: preserve existing readers explicitly if changing inheritance is necessary. Never broaden access merely to match the previous checkbox.                                                                               |
| 4. Prove the handoff         | Package administrator and independent reviewer | With separate authorization, publish a uniquely named rehearsal tag to the **same existing package**, with `org.opencontainers.image.source` set to the target monorepo URL. Confirm the _registry's_ linked repository changed, not just the image label. If GitHub does not support relinking in place, stop and resolve it; do not delete or recreate the package. Record package ID before/after, test digest, old digest pull, supported platforms, private visibility, and reader access. |
| 5. Switch the writer         | Package administrator                          | Remove the old repository's Actions grant and verify no inherited or explicit write path remains for its workflows. Review the final role of the monorepo. Keep the old publisher paused. Never test denial by overwriting a production tag.                                                                                                                                                                                                                                                    |
| 6. Release and observe       | Release maintainer                             | Only after sign-off, use a new per-bridge version and its reviewed tag. Confirm the correct image, source label, GitHub release, assets and documentation links. Keep existing immutable version tags and old release downloads intact.                                                                                                                                                                                                                                                         |

**Rollback:** Disable the target publisher and drain in-flight jobs. Restore the original association, visibility, reader access, inheritance and repository grants from the recorded settings. Verify the old writer and an existing reader still work, then reenable only the old publisher. Point clients to a known-good digest when necessary; do not overwrite an immutable release tag. Record the restored package ID and old digest pull.

**Rehearsal boundary:** Prove the procedure first with a disposable package and two distinct repository identities. A local build, a simulated role, or a successful test against a new package is not evidence of a completed production handoff. Publish nothing and change no live permissions without separate approval.

The [disposable rehearsal](../../migration/package-rehearsal.md) verified GitHub's manual relink procedure: **Package settings → Repository source → Unlink**, then **Connect Repository** on the package landing page. Verify the registry package ID across both steps. Publishing a new source label does not replace this step. Inspect Actions grants and inheritance separately after each relink; both can differ from the intended final settings.

## Independent version and release review

Keep Changesets entries and changelogs inside the six existing pnpm/Changesets bridge directories. Prepare a version PR from the owning directory, using its pinned `pnpm changeset version` command and reviewing the resulting package version, changelog and lockfile. Do not run it from the website root or combine unrelated version PRs. For Display and Modbus, review the Cargo package version, lockfile and the matching bracketed changelog entry together. For AdGuard Home, review its package version and changelog. Never auto-merge version PRs. Ping and IDM Energy have no package publisher.

After the version PR is merged, tag the reviewed main-branch revision as `<slug>/v<major>.<minor>.<patch>`. Use **Bridge release** from `main`. `dry-run` is the default: it validates the tag and builds one linux/amd64 image and any binary release artifacts without writing to the registry. `handoff-test` uses a unique non-production tag on the existing package and never moves `latest` or creates a release. `release` publishes that bridge's tested image, established aliases, scoped notes, and applicable assets. The Modbus archive retains its existing filename, layout, and SHA-256 sidecar.

Set `BRIDGE_RELEASE_PACKAGES` on the `bridge-release` environment to a JSON array of approved slugs. A maintainer starts the workflow manually from `main` and selects a mode; an authorized publish proceeds without a second deployment approval. Keep the environment restricted to the `main` branch. A missing or empty allowlist must block writes. Do not grant the workflow organization-wide credentials. If publishing fails after an immutable version was pushed, compare the registry digest with the tested artifact, complete only the missing aliases or release assets under separate approval, and record the partial result; do not rebuild and overwrite a published version.
