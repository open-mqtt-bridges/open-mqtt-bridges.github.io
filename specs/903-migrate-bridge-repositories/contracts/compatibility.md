# Contract: Builds, releases, and public interfaces

**Package ownership:** For each GHCR package, distinguish the organization that owns its namespace from the repository linked to the package and the repositories granted Actions access. Keep the organization and package name unchanged. Set the linked repository to the monorepo and grant its release workflow the required write access. For new images, set `org.opencontainers.image.source` to the monorepo URL; the label alone is not proof that GitHub changed the existing package association or its permissions. Check effective access, including inherited permissions, and preserve intended pull access. After verifying the handoff, revoke the old repository's publishing grant without removing unrelated consumers' read access.

- **CI:** Orchestrate jobs from `.github/workflows/` at the target root. Historical files under `bridges/<slug>/.github/workflows/` are not active workflows on the integrated branch. A bridge change runs that bridge's checks; changes to shared CI or build inputs run checks for every affected bridge. Use an always-running aggregate status for branch protection. Separate caches by bridge, toolchain, and lockfile. Archive and documentation-only changes must not release a bridge.
- **Releases:** Keep each bridge's version source, changelog, and existing Changesets state where applicable. Use new tags such as `wled/v1.2.3`; validate the exact slug and manifest version. Historical `import/**` tags, ordinary pushes, website version changes, and other bridges must not trigger a release. Scope release notes to the bridge. Do not share a single `latest` tag across bridges.
- **Distribution:** Preserve existing `ghcr.io/open-mqtt-bridges/<slug>` image names, version and architecture tags, and supported platforms per the inventory. Do not derive image names from the target repository name. Verify package linkage, write access, Docker context, and platforms per package. Pull an existing digest and test publishing under an isolated tag. Apply the same checks to other published artifacts. Do not introduce a publisher for Ping or the archive merely because they joined the monorepo.
- **Runtime:** Keep MQTT topics, payloads, retention behavior, configuration keys, health checks, CLI and Compose usage, and mount paths compatible. If an instruction for building from a source checkout needs a new path, document the replacement and link from the old entry point. Do not count simulation as a hardware acceptance test.
- **Documentation and hosting:** Preserve today's public routes, anchors, and publishers independently of feature 902. Check the current site and source builds; do not switch Pages providers or require a new central guide. Update source links in the catalog and organization profile only when their targets exist. Keep old release URLs, assets, issues, and PR discussions accessible; Git history does not contain them.
